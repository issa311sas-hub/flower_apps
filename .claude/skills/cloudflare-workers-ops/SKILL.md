# Cloudflare Workers 運用の落とし穴

`apps/cleaning-schedule` で実際に踏んだものだけを載せる。
どれも**画面上は正常に見えるのに動かない**類なので、知らないと切り分けに何時間もかかる。

## シークレットの登録パネルが2つある

ダッシュボードの「Variables and Secrets」は**2か所にある**。

| 場所 | 効く範囲 |
|---|---|
| Build カードの**中** | ビルド時のみ。**動いている Worker からは見えない** |
| Build カードの**外**（Settings 直下） | 実行時。アプリが読むのはこちら |

間違えると、登録したのに `env.XXX` が `undefined` になる。
**対策**: `/api/health` に「値そのものではなく、あるかどうか」を返す欄を作る。
さらに、鍵が入れ替わっていないかを**指紋**で確かめられるようにしておくと、
「IDまたはパスワードが違います」という無関係なメッセージで迷わずに済む。

## cron は UTC。日本時間ではない

`wrangler.jsonc` の `triggers.crons` は UTC。JST より9時間前。

| 書く値 | 実際に動く時刻(JST) |
|---|---|
| `0 21 * * *` | **翌朝6時** |
| `0 9 * * *` | 当日18時 |

`0 21` を「21時」と読み違えるのは半年後の自分がいちばんやる。コメントを必ず添える。

## Deploy command と Version command は別物

Workers Builds の Build configuration:

| 欄 | 使われるとき | cron の登録 |
|---|---|---|
| Deploy command (`npx wrangler deploy`) | 本番ブランチへの push | **される** |
| Version command (`npx wrangler versions upload`) | それ以外のブランチ | **されない** |

Deploy command が `versions upload` になっていると、
**コードは更新されるのに cron だけ動かない**。デプロイ履歴は成功に見える。
自動実行が動かないときは、Cron Triggers の登録の次にここを見る。

## ログは「Logs」ではなく「Observability → Events」

- 既定の期間が **Last 1 hour**。広げないと数時間前の事象は出ない
- 無料プランの保持は **3日**
- `wrangler.jsonc` に `"observability": { "enabled": true }` が要る
- cron の実行は URL ではなく `scheduled` 側の記録として出る

**ログを見に行かないと分からない状態にしない。**
判断に要る事実は、アプリ自身が `/api/health` に出す。

## 死活監視は HEAD → GET の順に来る

UptimeRobot などはまず `HEAD` で叩き、失敗したら `GET` でやり直す。
自作ルータがメソッド完全一致だと HEAD が404になり、

- 1回の巡回が2往復になる
- 監視を「HEAD のみ」にすると**健全なのに常時停止と誤検知する**

HEAD は GET と同じ状態・ヘッダを返し、本文だけ落とす（HTTP の規定）。
ルータに HEAD→GET のフォールバックを1つ入れておく。
ただし **POST 専用のパスを GET へ流してはいけない**（副作用のある処理を叩けてしまう）。

## Pages ではなく Workers Static Assets を使う

Pages Functions には **Cron Triggers が無い**。
定時処理があるなら最初から Workers + `assets` にする。静的ファイルの配信は同等。

## 無料プランの制限

| 項目 | 上限 |
|---|---|
| CPU 時間 | 1リクエスト 10ms（**I/O 待ちは含まれない**ので外部APIは何度でも叩ける） |
| サブリクエスト | 1リクエスト 50 |
| cron | ベストエフォート。**遅延・取りこぼしがありうる** |

外部APIをページングで叩くときは、終了条件が壊れても暴走しないよう
ページ数の上限を必ず入れる。

## 監視をつくるときの原則

`apps/cleaning-schedule/docs/decisions.md` に、同じ形の不具合が4件並んでいる。

1. 直ったのに警告が消えない
2. 見張り役が滞留の判定時計を毎日リセットしていた
3. 「呼ばれていない」と「呼ばれたが落ちた」が同じ見え方だった
4. 死活監視の窓口が HEAD に404を返していた

共通しているのは **監視の仕組みそのものが検証されていなかった**こと。

- 判定は派生した設定値ではなく、**いちばん元の記録**から引く
- 分岐する前に記録を取る。「記録が無い」は情報にならない
- 自動で復旧する仕組みは、**復旧したことで故障を隠さない**ようにする
- 「通っていること」ではなく「**正しい経路で**通っていること」を確かめる

# v8 - 2026-09-04 稼働監視・異常通知

## 変更理由

管理者の不在中（旅行中）にBeds24のリフレッシュトークンが失効し、
清掃予定の自動反映が停止していたが、誰も気づけなかった。

原因は2点。

1. `runAllAuto()` が全てのエラーを `catch` して `Logger.log` に書くだけだったため、
   Apps Script から見ると「正常終了」となり、Googleの実行失敗通知メールも飛ばなかった
2. リフレッシュトークンは30日間使われないと失効するが、
   日次トリガーが止まった時点で誰にも通知されないまま失効まで進行した

## 変更内容

### 1. メール通知（新規追加）
- `notifyOwner_(subject, body, throttleKey)` を追加。スクリプト実行者宛にメール送信
- 同じ種類の通知は12時間に1回まで（`NOTIFY_THROTTLE_HOURS`）
- 通知するケース:
  - リフレッシュトークンの失効（401/403）→ 復旧手順つきで通知
  - Beds24への一時的な接続エラー
  - 自動実行がエラーで停止
  - 取得件数が0件
  - 未割当（要確認）が残っている
  - 3日以上、自動実行が正常終了していない
  - トークンが20日間使われていない（失効の20日前に予告）

### 2. キープアライブトリガー（新規追加）
- `beds24KeepAlive()` を追加し、全自動実行とは**別のトリガー**（12時間ずらし）で日次実行
- 役割:
  1. リフレッシュトークンを能動的に使って失効を防ぐ（`getBeds24AccessToken_(true)`）
  2. 全自動実行が何日も成功していない場合に通知
  3. トークンの失効が近い場合に通知
- 全自動実行側が壊れても、見張り役が生き残って異常を知らせる

### 3. トークン失効の検知と可視化
- `getBeds24AccessToken_()` に `forceRefresh` 引数を追加
- HTTP 401/403（失効・取り消し）と、それ以外（一時的障害）を区別して扱うようにした
  - 401/403 → 設定シートB15を `要再接続 ✗` にし、復旧手順をメール通知
  - それ以外 → トークンは保持し、一時的障害として通知
- トークンを最後に更新できた日時を `BEDS24_TOKEN_LAST_OK` に記録

### 4. 稼働状態の記録・確認
- メニューに「🩺 稼働状態を確認」を追加
  - トリガーの設定状況、最終正常終了日時、トークンの残り日数、通知先を一覧表示
- 設定シートに「最終自動実行」（A18/B18）を追加し、毎回の実行結果を記録
  - 既存シートにも実行時に自動で書き込まれる（初期設定のやり直しは不要）

## 導入手順（既存環境の更新）

1. `src/Code.gs` の中身をApps Scriptエディタに貼り付けて保存
2. スプレッドシートを再読み込み
3. 「🧹 清掃管理 → ⏰ 日次自動実行を設定」を実行し直す
   （キープアライブ用のトリガーが追加されるため、必ず再設定が必要）
4. 「🧹 清掃管理 → 🩺 稼働状態を確認」で、トリガー2つと通知先を確認

> 初回実行時にメール送信の権限承認を求められます。

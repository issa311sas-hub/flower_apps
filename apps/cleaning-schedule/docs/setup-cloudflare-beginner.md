# Cloudflare 接続手順（はじめて触る人向け・Windows・ブラウザだけで完結）

このページの通りに進めれば、システムがインターネット上で動き出します。
**ターミナル（黒い画面）も Node.js のインストールも不要**です。すべてブラウザで完結します。

所要時間: 40〜60分。途中で分からなくなったら、その時点で聞いてください。

---

## この作業で何が起きるのか（先に全体像）

```
  ① Cloudflareのアカウントを作る
        ↓
  ② データの保管場所（D1）を作る          ← 予約・割り当て・出勤可否を入れる箱
        ↓
  ③ Database ID を開発者に渡す            ← ここで一度止まります
        ↓
  ④ GitHubの既定ブランチを main にする     ← これを忘れると⑤が必ず失敗します
        ↓
  ⑤ GitHubのコードとCloudflareをつなぐ     ← 以降、コードを更新すると自動で反映される
        ↓
  ⑥ 秘密の鍵を2つ登録する
        ↓
  ⑦ /setup を開く                        ← 表・初期データ・管理者アカウントができる
        ↓
  ⑧ 動いているか確認する
        ↓
  ⑨ Beds24 につないで対応づけを登録する     ← ★ここまでやらないと予約が入りません
        ↓
  ⑩ 予約を取り込んでみる
        ↓
  ⑪ スタッフのアカウントを作る
        ↓
  ⑫ Slackへの通知を設定する               ← 止まったときに気づくため
        ↓
  ⑬ 外部から死活監視する                   ← システムごと止まった場合の備え
```

> **SQLを手で貼る作業はありません。** ⑦でURLを開くだけで、15個のテーブルと
> 初期データ（9ユニット・担当者4名）が自動で作られます。

**用語**（初回だけ気になるので）

| 言葉 | 意味 |
|---|---|
| Cloudflare | 今回システムを動かす場所。無料枠で足ります |
| Workers | プログラムを動かす仕組み。今回のシステム本体 |
| D1 | Cloudflare のデータベース。予約や割り当てを保存する場所 |
| cron（クーロン） | 決まった時刻に自動実行する仕組み。毎朝6時の処理に使います |
| デプロイ | 書いたコードを実際に動く状態にすること |

## ① Cloudflare のアカウントを作る

1. https://dash.cloudflare.com/sign-up をブラウザで開く
2. メールアドレスとパスワードを入れて登録
   - **クレジットカードの登録は不要**です。求められたらプラン選択を間違えている可能性があります
3. 確認メールが届くのでリンクをクリックして有効化
4. ログインすると「Cloudflare ダッシュボード」が開きます。ここが今後の作業場所です

> **名義について**: 今回はあなたのアカウントで作ります。将来経営者に引き継ぐ可能性があるなら、
> あとで **Manage Account → Members → Invite** から経営者を Administrator として招待しておくと、
> 名義変更よりずっと簡単に移せます。今やらなくても大丈夫です。

---

## ② データの保管場所（D1）を作る

1. 左メニューの **Storage & Databases** をクリック → **D1 SQL Database** を選ぶ
2. **Create** ボタンを押す
3. Database name に **`cleaning-schedule`** と入力
   - ⚠ この名前は正確に入れてください。プログラム側の設定と一致していないと動きません
4. **Create** を押す

作成されると、そのデータベースの画面が開きます。この画面はこの後も使います。

---

## ③ Database ID を開発者に渡す

**テーブルを作る作業はここではやりません。**（⑦で自動的に作られます）

1. データベース画面の右側（または Settings）に **Database ID** が表示されています
2. `1a2b3c4d-...` のような文字列です。**これをコピーしてチャットに貼ってください**
   - このIDは秘密情報ではありません（これだけでは誰もアクセスできません）
   - ⚠ ただし後で出てくる **API トークンと2つの鍵は絶対に貼らないでください**

開発者がプログラム側の設定ファイル（`wrangler.jsonc`）にこのIDを書き込んで反映します。
**ここで一度作業が止まります。** 反映が終わったら④に進みます。

## ④ GitHub の既定ブランチを `main` にする（先にやること）

⚠ **これを先にやらないと、次の⑤で必ずビルドが失敗します。**

このリポジトリの既定ブランチは、いま `claude/agent-team-skills-review-w07g3a` という
古い作業用ブランチになっています。そのブランチには清掃予定管理のコードが入っていません。
Cloudflare は既定ブランチを本番用として自動で選ぶため、切り替えておく必要があります。

1. https://github.com/issa311sas-hub/flower_apps を開く
2. **Settings**（リポジトリの設定。上部のタブ） → 左メニューの **Branches**
3. **Default branch** の欄にある切り替えボタン（⇄ のアイコン）を押す
4. **`main`** を選んで **Update** → 確認ダイアログで **I understand, update the default branch**

これで既定ブランチが `main` になります。

> **すでに⑤（Cloudflareへの接続）をやってしまった場合**は、この切り替えだけでは直りません。
> Cloudflare 側にも接続時のブランチが保存されているため、
> ⑤の「[古いブランチのまま作ってしまった場合の直し方](#-古いブランチのまま作ってしまった場合の直し方)」を見てください。

## ⑤ GitHub のコードと Cloudflare をつなぐ

ここまでで箱ができました。次は中で動くプログラムを載せます。
一度つないでおけば、**以降はコードを更新するだけで自動で反映**されます。

1. 左メニューの **Workers & Pages** をクリック
2. **Create application** を押す
3. **Import a repository**（リポジトリを取り込む）の側にある **Get started** を押す
4. GitHub アカウントの接続を求められるので許可する
   - リポジトリを選ぶ画面で `issa311sas-hub/flower_apps` を選択
   - 「すべてのリポジトリ」ではなく、このリポジトリだけを許可すれば十分です
5. 設定画面が出るので、次のとおり入力します

| 画面の項目 | 入れる値 | 補足 |
|---|---|---|
| Project name | `cleaning-schedule` | URL の一部になります |
| Build command | `npm test` | テストが落ちたらデプロイされない安全装置になります |
| Deploy command | `npx wrangler deploy` | |
| **Path**（Advanced settings の中） | **`apps/cleaning-schedule`** | ⚠ **ここが最重要。** 既定は `/` になっています。必ず書き換えてください |
| Non-production branch deploy command | そのまま（`npx wrangler versions upload`） | 変更不要 |
| API token | **Create new token** のまま | |
| API token name | `cleaning-schedule-builds` など任意 | Cloudflare が自分で作って保持します。**どこかに貼る必要はありません** |

6. **Deploy** を押す

初回は3〜5分かかります。ログが流れるので眺めていてください。

### 迷いやすいところ

- **「Root directory」という名前の欄はありません。** 画面では **Path** です。
  Advanced settings（詳細設定）を開かないと出てきません。
  ツールチップに「The root directory describes where the command(s) will run」と書かれているのが目印です。
- **「Production branch」の欄が見当たらない場合**は、④で既定ブランチを `main` にしてあれば
  自動的に `main` が使われるので、そのまま進めて構いません。
  作成後に **Settings → Builds** から変更もできます。
- 画面の項目名は Cloudflare 側の更新で変わることがあります。
  探している項目が見つからないときは、まず **Advanced settings** を開いてみてください。

### 失敗したときの見方

#### ログの開き方

1. **Workers & Pages** → `cleaning-schedule` → **Deployments** タブ
2. **Build history**（このworkerのビルド一覧）が出ます。赤い ● が付いていたら失敗です
3. その行の右にある **View build** をクリック
4. ビルドログが開きます

> **⚠ Observability タブではありません。** 紛らわしいのでご注意ください。
>
> | 場所 | 何のログか |
> |---|---|
> | **Deployments → View build** | **ビルド時**のログ（`npm test` や `wrangler deploy` の出力）← 今見たいのはこちら |
> | Observability | **稼働後**のログ（デプロイ済みのアプリへのアクセス記録）。まだデプロイが成功していない段階では何も出ません |

#### ログの読み方

上から順に「リポジトリの取得 → 依存関係のインストール → `npm test` → `npx wrangler deploy`」と流れます。
**赤い文字や `Error` / `failed` が最初に出てくるところ**が原因です。

| ログに出るもの | 意味 |
|---|---|
| `Tests 105 passed` | テスト通過。ここまで来ていればコードは正常です |
| `Cloning repository...` の直後で失敗 | ブランチやリポジトリ設定の問題 |
| `npm ci` で失敗 | Root directory の指定ミス（`package.json` が見つかっていない） |
| `npx wrangler deploy` で失敗 | 設定（`wrangler.jsonc`）や D1 まわりの問題 |

原因が分からないときは、**最初のエラーが出ている行から下20行くらい**をコピーして開発者に渡してください。

#### まず Source 列を見る（ログを読む前に）

Build history の **Source** 列に、どのブランチからビルドしたかが出ています。

```
Source                              Status
claude/agent-team-skills-review-w…  ● 失敗    ← main になっていない
```

**ここが `main` 以外なら、ログを読むまでもなくそれが原因です。**
古いブランチには `apps/cleaning-schedule` が入っていないので、Path が正しくても必ず失敗します。

#### ⚠ 古いブランチのまま作ってしまった場合の直し方

**GitHub 側で既定ブランチを `main` に変えても、Cloudflare 側の設定は自動では変わりません。**
接続した時点のブランチが保存されたままなので、Cloudflare 側でも変更が必要です。

1. GitHub の既定ブランチを `main` にする（④。まだなら先にこちら）
2. Cloudflare → **Workers & Pages** → `cleaning-schedule` → **Settings** → **Builds**
3. 少し下にスクロールして **「Branch control」** という見出しを探す
   - その下の **Production branch** がブランチの設定です
   - ドロップダウン（右端の ▼）を押して **`main`** を選び、保存する
4. ついでに上の **Build configuration** も確認する
   - **Root directory** が `apps/cleaning-schedule`（`/` や空欄なら修正）
   - Build command が `npm test`
   - Deploy command が `npx wrangler deploy`
5. **Retry build**（再実行）を押す。または `main` に何か push すれば自動で走ります

Source 列が `main` になって成功すればOKです。

> **画面によって呼び名が違うので注意**
>
> | 作成画面（Create an app） | 設定画面（Settings → Builds） |
> |---|---|
> | **Path**（Advanced settings の中） | **Root directory**（Build configuration の中） |
> | 表示されないことがある | **Production branch**（**Branch control** の中） |
>
> 同じものを指しています。作成時に見つからなかった項目も、設定画面には必ずあります。

#### そのほかの原因

| ログに出る内容 | 原因 |
|---|---|
| `package.json` が見つからない | **Path** の指定漏れ（`/` のままになっている） |
| `Missing entry-point` / `public` が無い | コードが古い。最新の `main` になっているか確認 |
| `database_id` に関するエラー | ③のIDが設定に入っていない |
| テストの失敗 | プログラム側の問題です。ログを貼ってください |

## ⑥ 秘密の鍵を2つ登録する

ログインの仕組みと、Beds24 のトークンを暗号化して保存するために使います。

> ⚠ **⑦より先に、ここを済ませてください。**
> `SESSION_PEPPER` はログインのパスワードを守るために使います。
> 鍵が無い状態で⑦を開いて管理者アカウントを作ってしまうと、
> あとから鍵を登録したときにそのパスワードでは入れなくなります。

### 値を作る

ブラウザで次のURLを開いてください。**2つの値が表示されます。**

```
https://cleaning-schedule.<あなたのサブドメイン>.workers.dev/setup/keys
```

それぞれの右にある「コピー」ボタンで値をコピーできます。

> この2つはパスワードと同じ扱いです。**チャットにも貼らないでください。**
> 登録し終えたらこのページは閉じてください。

> **⚠ 「開発者ツールのコンソールにコードを貼る」方法は使いません**
>
> 以前の手順書ではその方法を案内していましたが、ブラウザが次の警告を出して止めます。
>
> ```
> Don't paste code into the DevTools Console that you don't understand...
> Type "allow pasting" ...
> ```
>
> **この警告は正しい保護です。「allow pasting」と入力して解除しないでください。**
> 「コンソールにこれを貼ってください」というのは、他人のアカウントを乗っ取る詐欺の
> 典型的な手口です。今後もし誰かにそう言われたら、それは危険な指示だと思ってください。
> このシステムでは、その操作が必要な場面はありません。

### 登録する

1. **Workers & Pages** → `cleaning-schedule` を開く
2. **Settings** タブ → **Variables and Secrets**
3. **Add** を押し、次の2つを登録する（Type は必ず **Secret** を選ぶ）

> ⚠ **「Variables and Secrets」は Settings の中に2か所あります。**
>
> | どこにあるか | いつ使われるか |
> |---|---|
> | **Build** のカードの中（Git連携・ビルドコマンドの設定と同じ枠） | **ビルド中だけ**。動いているアプリからは見えません |
> | **Build のカードの外**（Bindings と並んでいる方） | ← **こちらが正解**。動いているアプリから読めます |
>
> 見た目がほとんど同じで、間違えても登録自体は成功してしまいます。
> **登録したのに `/api/health` の `secrets` が `false` のままなら、ビルド用の方に入っています。**
> Build のカードの外にある方へ登録し直してください。

| Variable name | Value |
|---|---|
| `SESSION_PEPPER` | `/setup/keys` に出た1つ目の値 |
| `TOKEN_ENC_KEY` | `/setup/keys` に出た2つ目の値 |

4. **Deploy**（保存して再デプロイ）を押す

> 画面を再読み込みすると別の値が出ますが、問題ありません。
> 登録に使うのは1回だけです。

> ⚠ **一度登録したら、あとから作り直さないでください。**
> - `SESSION_PEPPER` を変えると、**全員がログインできなくなります**
> - `TOKEN_ENC_KEY` を変えると、**Beds24 のトークンを読めなくなり、つなぎ直しが必要になります**
>
> 登録済みかどうかは `/api/health` の `secrets` で確認できます（値は出ません）。
> 2つとも登録済みの状態で `/setup/keys` を開くと、
> 「登録済みです」とだけ表示され、**新しい鍵は作られません**。

> **なぜ Beds24 のトークンは Secret に入れないのか**
> Beds24 はトークンを使うたびに新しいものを発行し直す仕組み（ローテーション）です。
> Cloudflare の Secret は動作中のプログラムから書き換えられないため、Beds24 のトークンは
> D1 に暗号化して保存します。`TOKEN_ENC_KEY` はその暗号化に使う鍵です。

## ⑦ /setup を開いてテーブルを作る

ここまでで、プログラムは動いているがデータベースは空っぽ、という状態です。
ブラウザで次のURLを開くだけで、テーブルと初期データが作られます。

```
https://cleaning-schedule.<あなたのサブドメイン>.workers.dev/setup
```

**「セットアップが完了しました」** と表示され、次の内容が出れば成功です。

| テーブル | 15 個 |
|---|---|
| ユニット | 9 件 |
| 担当者 | 4 名 |

> **2回開いても大丈夫です。** すでに完了している場合は「すでに完了しています」と表示され、
> データには一切触りません。うっかり再読み込みしても壊れません。

> ⚠ **`/setup` と `/setup/keys` は別の画面です。**
> アドレス欄が履歴から補完されて、⑥で使った `/setup/keys`（鍵を作る画面）が
> 開いてしまうことがあります。**鍵の値が並んでいたら、それは `/setup/keys` です。**
> 末尾の `/keys` を消して開き直してください。
> `/setup` には「セットアップの進み具合」のチェックリストが出ます。

### 管理者アカウントが1回だけ表示されます

初めて `/setup` を開いたとき、**管理者のIDとパスワード**が同じ画面に表示されます。

| ID | `admin` |
|---|---|
| パスワード | **この画面にしか表示されません** |

**閉じると二度と表示されません。**必ず控えてから閉じてください。
（ログインすると、すぐに自分の覚えやすいパスワードへの変更を求められます）

> 2回目以降に `/setup` を開くと、**ログインを求められます。**
> 管理者が居る＝運用が始まっている状態なので、データベースの中身を
> 誰にでも見せないようにしています。

#### パスワードを控え損ねたとき／鍵を後から登録してしまったとき

管理者アカウントを消して作り直せます。**⑥の鍵を後から登録した場合も同じ手順です**
（鍵が変わるとパスワードの照合結果が変わり、正しいパスワードでも入れなくなるため）。

1. Cloudflare → **Storage & Databases → D1** → `cleaning-schedule` → **Console**
2. 次の**1行だけ**を貼って **Execute**

   ```sql
   DELETE FROM users WHERE login_id = 'admin';
   ```

3. もう一度 `/setup` を開くと、新しいパスワードが表示されます

> このための「リセット用URL」はあえて作っていません。
> 誰でも開けてしまい、乗っ取りの入口になるためです。
> D1 の Console は、Cloudflare にログインできる人（＝あなた）しか使えません。

### エラーが出たら

| 表示 | 原因と対処 |
|---|---|
| データベースにつながっていません | `database_id` が設定に入っていません。開発者に連絡してください |
| セットアップに失敗しました | 表示されたメッセージをそのまま開発者に貼ってください |

## ⑧ 動いているか確認する

次の5つを確認できたら完了です。

### 1. サイトが開く

`https://cleaning-schedule.<あなたのサブドメイン>.workers.dev`

**ログイン画面**が出ます。ここに、⑦で控えた ID `admin` とパスワードを入れます。

### 2. データベースにつながっていて、中身も入っている

上のURLの末尾に `/api/health` を付けて開きます。

```json
{
  "ok": true,
  "stage": "m5",
  "d1": {
    "connected": true,
    "units": 9,
    "staff": ["細田さん", "普久原さん", "福田さん", "Rクリーン"],
    "users": 1,
    "unitMap": 0
  },
  "beds24": { "state": "未接続", "connected": false },
  "secrets": { "SESSION_PEPPER": true, "TOKEN_ENC_KEY": true }
}
```

`"ok": true` で、`units` が 9、`staff` に4名出ていればD1との接続まで通っています。
`"ok": false` の場合は `error` に理由が書いてあるので、その文面を貼ってください。

この画面は**中身を一切表に出しません**（鍵は「登録されているか」だけ、
Beds24 のトークンは出ません）。そのままの内容を貼って構いません。

| 項目 | 見るところ |
|---|---|
| `stage` | いま動いているバージョン。手順書と食い違うときは、まだデプロイが終わっていません |
| `users` | ログインできる人の数。⑦の直後は 1（管理者だけ） |
| `unitMap` | ユニットの対応づけの件数。**0 のままだと予約を1件も取り込めません**（⑩で登録します） |
| `secrets` | 両方 `true` になっていること |

### 3. 自動実行が登録されている

**Settings** → **Triggers**（またはCron Triggers）に2件あるか確認します。

| cron | 実際に動く時刻（日本時間） | 役割 |
|---|---|---|
| `0 21 * * *` | 毎日 **翌朝6時** | Beds24取得 → 割り当て → 通知 |
| `0 9 * * *` | 毎日 **18時** | トークンの維持・稼働監視 |

> ⚠ **cron の時刻は UTC（世界標準時）で書きます。** 日本時間より9時間遅れです。
> `0 21` は「21時」ではなく「翌朝6時」。ここは半年後に見て混乱しやすいので覚えておいてください。

### 4. GitHub 側のテストも通っている

GitHub のリポジトリ → **Actions** タブ → 最新の実行が緑のチェックになっていること。

### 5. コードの更新が自動で反映される

以降、コードを更新して `main` に反映すると、Cloudflare が自動でテスト→デプロイします。
**あなたがターミナルを触ることはもうありません。**

## ⑨ Beds24 につないで、ユニットの対応づけを登録する

ここが**一番大事な工程**です。これが終わるまで、予約は1件も入ってきません。

### 1. 招待コードを発行する

Beds24 の管理画面で発行します。

1. Beds24 にログイン → **SETTINGS → MARKETPLACE → API**
2. 招待コード（invite code）を発行する
3. スコープに **`bookings`** と **`properties`** が含まれていることを確認する

> ⏰ **招待コードは発行から24時間で失効します。** 発行したらすぐ次へ進んでください。
> 失効しても、また発行し直せば大丈夫です。

> 現行の GAS 版とは**別のコード**を発行します。両方が同時につながった状態にして、
> しばらく結果を見比べてから切り替えます。

### 2. このシステムにつなぐ

管理画面 → **「Beds24・ユニット対応づけ」** を開き、招待コードを貼って **接続する**。

「状態」が **接続済み** になれば成功です。

| 表示 | 意味と対処 |
|---|---|
| 接続に失敗しました | コードが違う／期限切れ／スコープ不足。発行し直してください |
| 先に秘密の鍵（TOKEN_ENC_KEY）を登録してください | ⑥が終わっていません |

### 3. ユニットの対応づけを登録する

Beds24 の部屋番号（`roomId:unitId`）が、こちらの **b2〜c4 のどれに当たるか**の表です。
**この表が空だと、予約を取得できても1件も取り込めません。**

1. **「Beds24 からルームIDを調べる」** を押す
2. 予約に出てくる部屋の一覧が、**予約数つき**で表示される
3. 各行で、対応するユニット（b2〜c4）を選ぶ。使わない部屋は「（使わない）」のまま
4. **「対応づけを保存」** を押す

> 旧システムのスプレッドシートの「設定」シート21行目以降にも同じ表があります。
> 迷ったらそちらと突き合わせてください。

> ⚠ 保存すると**表に出ている内容がそのまま全体になります。**
> 取得期間にたまたま予約が無かった部屋は「今回は出てきません」と表示されますが、
> その行も一緒に保存されるので消えません。**行を消さずにそのまま保存してください。**

## ⑩ 予約を取り込んでみる

管理画面のトップで **「いま実行する」** を押します。
Beds24 から予約を取り直し、担当を割り当て直します。20秒ほどかかることがあります。

| 取得できた予約が0件でした | 対応づけが合っていない可能性が高いです。⑨-3 をやり直してください |

**ここが移行で一番大事な確認です。**
旧システムの「割り当て結果」シートと、この画面の一覧を見比べてください。
同じ予約に同じ担当が付いていれば、移植が正しくできています。

あわせて、**旧システムが止まっていないこと**も確認してください
（旧版の「システム状態」シート）。両方動いている状態で、しばらく結果を見比べます。

## ⑫ Slack への通知を設定する

**旧システムが旅行中に静かに止まり、誰も気づけなかった**——それを繰り返さないための工程です。
いまは戻れる旧システムがないので、ここは省略しないでください。

### 1. Slack で Incoming Webhook を作る

1. Slack の管理画面（`https://<ワークスペース>.slack.com/apps`）で **Incoming Webhooks** を開く
2. 通知を受けたいチャンネルを選んで追加する
3. 表示された **`https://hooks.slack.com/services/...`** をコピーする

### 2. このシステムに登録する

管理画面 → **「設定・Slack通知」** → **Slack の Webhook URL** に貼り付けて **保存する**。

- パスワードと同じ扱いです。暗号化して保存され、この画面に再表示されることはありません
- 保存したら **「Slack にテストを送る」** を押して、実際に届くか確認してください

> ⚠ **スタッフの出勤入力より先に「いま実行する」を押した場合**
>
> 出勤入力が空の状態で実行すると、直近14日分がすべて **Rクリーン（外注）** に落ちます。
> 割り当ては前回の担当を引き継ぐ設計なので、**あとから出勤入力を入れても
> 自動では戻らない場合があります**。
> そのときは管理画面の **「ゼロから割り当て直す」** を1回押してください。
> 手で固定した分と、完了報告が済んだ分はそのまま残ります。

### 3. 何が通知されるか

| いつ | 通知 |
|---|---|
| 毎朝、正常に終わったとき | ✅ 割り当ての件数（1日1回） |
| 担当が決まらない清掃があるとき | ⚠️ 未割当◯件 |
| 自動実行が失敗したとき | ❗ エラーの内容 |
| Beds24 の再接続が必要なとき | ❗ 復旧手順つき |
| 何日も成功していないとき | ❗ 何日止まっているか |

> **正常時の通知を切らないでください。**
> 「いつも届くものが届かない」ことが、止まっていることに気づく手がかりになります。
> どうしても多いと感じたら、設定画面のチェックを外せば異常時のみになります。

## ⑬ 外部から死活監視する（推奨・無料）

Slack 通知には**弱点が1つ**あります。**システムごと止まったときは、通知を送る側も止まっている**ので何も届きません。
これを補うために、外部のサービスから定期的に呼んでもらいます。

`/api/health` は、異常があると **HTTP 503** を返すように作ってあります。
ステータスコードを見るだけの単純な監視サービスで、そのまま使えます。

1. 無料の監視サービス（UptimeRobot、Better Stack など）に登録する
2. 監視するURLに次を設定する

   ```
   https://cleaning-schedule.<あなたのサブドメイン>.workers.dev/api/health
   ```

3. 間隔は5〜30分で十分です。通知先をメールか Slack にする

これで次の3つが外から検知できます。

| 状態 | 応答 |
|---|---|
| 正常 | 200 |
| 自動実行が◯日成功していない／Beds24 の再接続が必要／誰もログインできない | **503** |
| Cloudflare ごと落ちている | 応答なし |

> この画面は中身を一切表に出しません（鍵は「登録されているか」だけ、トークンは出ません）。
> 監視サービスに URL を登録して問題ありません。

## データベースの更新があったとき

機能を足すとき、データベースに新しい表が必要になることがあります。
その場合、**管理画面のいちばん上に赤い枠で「データベースの更新が◯件あります」**と出ます。
その中の **「いま更新する」** を押してください。それだけで終わります。

- 何度押しても、同じ更新が二重に流れることはありません
- 既存のデータには触りません
- 押し忘れても、**翌朝の自動実行のときに自動で当たります**
- それでも当たっていなければ `/api/health` が **503** を返し、UptimeRobot から通知が来ます

## よくあるつまずき

### 「The request is malformed: Requests without any query are not supported.」

D1 の Console で SQL を実行したときに出るエラーで、
**「有効なSQL文が1つも入っていない」** という意味です。
コメント（`--` で始まる行）だけの部分や、空っぽの状態で実行すると出ます。

**この手順書では Console に SQL を貼る作業自体をなくした**ので、通常は出ません。
もし以前の手順で試して出た場合は、次のように切り分けてください。

1. Console に `SELECT 1;` だけを貼って **Execute**
   - これも同じエラーになる → Console の使い方の問題（貼り付けができていない可能性）
   - これは成功する → 貼ったSQLの側の問題。⑥の `/setup` を使えば解決します
2. **途中までテーブルができてしまった場合**は、そのD1を削除して作り直すのが最短です
   （まだデータは何も入っていないので、消して困るものはありません）
   - D1 の画面 → Settings → Delete → もう一度②から
   - 作り直すと Database ID が変わるので、新しいIDを開発者に渡してください

> `/setup` は「テーブルがない」「初期データがない」状態からでも復旧できるようになっています。
> 途中まで進んでしまった場合でも、多くはそのまま `/setup` を開けば続きから完了します。

### どうしても手でSQLを流したい場合

`/setup` が使えないときの保険として、**コメントを取り除いたSQL**を用意してあります。
`migrations/console/` の3ファイルを、この順に Console へ貼って実行してください。

1. `01-tables.sql`（テーブル作成）
2. `02-indexes.sql`（インデックス作成）
3. `03-seed.sql`（初期データ）

## 困ったときの連絡の仕方

うまくいかないときは、次のどれかを貼ってもらえると原因が特定できます。

- Builds タブの**失敗したビルドのログ**（最後の20行くらい）
- `/api/health` の**表示内容そのまま**
- D1 Console でエラーが出たなら、その**エラーメッセージ**

**API トークン・`SESSION_PEPPER`・`TOKEN_ENC_KEY` の値は貼らないでください。**
それ以外（database_id、URL、エラーメッセージ）は貼って問題ありません。

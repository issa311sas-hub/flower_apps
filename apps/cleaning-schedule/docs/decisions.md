`apps/schedule-auto-assign/docs/decisions.md`（GAS 版 v1〜v8）の続き。
業務ルールそのものの経緯は旧アプリのログを参照すること。ここには Web 版の判断を記録する。

## 2026-09-08 Web アプリ化の方針決定

### 背景

清掃スタッフが Google カレンダーを使いこなせず、スマホの容量を理由にアプリも入れられない。
現行仕様は「カレンダーに数字の入力がない日＝出勤不可」というフェイルセーフのため、
**入力が定着しないことがそのまま Rクリーン外注のコスト増につながる**構造になっていた。

### 決定事項（経営者と確認済み）

| 項目 | 決定 |
|---|---|
| 移行方法 | 一気に完全移行。GAS + スプレッドシートは廃止（旧アプリは凍結して残す） |
| Google カレンダー | 完全にやめる。Web アプリを唯一の正とする |
| ログイン | 管理者が ID とパスワードを発行して各自に配る（厳密なセキュリティは不要） |
| 管理画面 | Web の管理画面も作る |
| 異常通知 | Slack の Incoming Webhook（＋管理画面のバナー） |
| 公開URL | `*.workers.dev` のまま（独自ドメインなし） |
| 完了報告ボタン | 入れる（現行にない新機能） |
| 既存の割り当て | 移行せず、新システムで全部再計算する |

### 技術方針

- **採用: Cloudflare Workers（静的アセット）+ D1 + Cron Triggers**
  - 当初の要望は Cloudflare Pages だったが、**Pages Functions は Cron Triggers に対応していない**。
    日次の自動実行がこのシステムの中心であるため、Pages 単体では成立しない。
    現在の Workers は静的配信で Pages と同等のため、デプロイ単位を1つにまとめられる Workers を選んだ。
- **不採用: SPA（React/Preact 等）** → 利用者は非エンジニアで端末も古い。画面は一覧とフォームのみで、
  フレームワークが買うものがない。サーバーレンダリングなら初回表示が速く、JS が壊れても画面は出る。
- **不採用: KV / Durable Objects** → D1 だけで足りる（セッション・設定・スロットルもテーブルで持つ）。
- **Beds24 のリフレッシュトークンは D1 に暗号化して保存する**
  → Cloudflare の Secrets は実行中に書き換えられないが、Beds24 はトークン取得のたびに
    ローテーションするため、Secrets には置けない（暗号鍵だけを Secret にする）。

### 日付の扱い（移行で最も壊れやすい点）

GAS はスクリプトのタイムゾーン（JST）で動いていたが、**Workers は UTC**。
そのため以下を規約とし、`test/core/purity.test.js` で機械的に検査する。

- カレンダー上の1日は必ず `'YYYY-MM-DD'` の文字列で表す
- 日付演算は `src/core/dates.js` に閉じる。`new Date(y, m, d)` と `setDate()` は使わない
- 実時刻に触れてよいのは `jstToday()` / `nowIso()` のみ
- cron は UTC 指定（`0 21 * * *` = 翌日 06:00 JST）

## 2026-09-08 割り当てエンジンの移植方針

8版かけて実運用で調整されたロジックのため、**まず現行と同一挙動で移植し、
テストで固定してから改善を検討する**という順序を徹底する。

### 新旧一致テスト（parity test）

旧 GAS 版の `doMatching_` をほぼバイト単位でコピーした比較用エンジン
（`test/legacy/legacy-engine.mjs`。I/O の4か所と実行日だけを引数に差し替えたもの）を用意し、
シード固定のランダムシナリオ2000件（延べ10万件以上の割り当て）で
新実装との出力一致を検証している。**現時点で完全一致。**

### 意図的に変えた点

1. **スタッフ名のベタ書きを廃止**し、`priority` 順のループに一般化した。
   旧版は「細田さん・普久原さん・福田さん」を名前で直接参照し、3名揃わないと例外を投げていた
   （FAQ「スタッフを追加・変更したい → コード変更が必要」の原因）。
   3名・同じ順序であれば計算結果は旧版と完全に一致する。
2. **Rクリーンを `kind: 'outsource'`** として扱う（旧版は文字列 'Rクリーン' を直接比較）。
3. **`isManual`（管理者の手動変更）の行を全フェーズで凍結する**。
   旧版に対応する処理はなく、Google カレンダー側の「同期状態=手動」が担っていた役割を移した。
   凍結された行も枠（usage）は消費する。
4. 日付を Date から文字列に変更（上記のとおり）。

### 現状維持とした「癖」（移植では直さない）

| 箇所 | 現行の挙動 | 扱い |
|---|---|---|
| Phase 2.5（Code.gs:835） | 入れ替え判定で既定上限を 0 固定にし、設定値を無視 | 既定値が全員0の現在は無害。そのまま移植 |
| Phase 3・4 | `usageByDate` を更新しない | そのまま移植 |
| Phase 4（Code.gs:915） | コスト最適化を「その予約のゲスト数」で比較。外注費は本来「次に泊まる人数」に連動するのでは | ⚠ 稼働後に経営者へ確認 |
| `computeDiff_` | 変更検知はチェックアウト日とユニットのみ（タイトル変更では再割り当てしない） | v7 の意図的な修正。維持 |

## 2026-09-08 【修正済み】次の予約がないユニットが延期できなかった件

### 見つかったこと

`docs/requirements.md` と旧 `decisions.md` には清掃期限を

> 清掃期限 = min(次の予約の開始日 - 1日, チェックアウト日 + 2日)

と記載しているが、**実装はそうなっていない**（`Code.gs:488, 500-509`）。
次の予約が見つからない場合、期限はチェックアウト**当日**のままで、
`canDefer` が false になる。つまり **次の予約がないユニットは1日も延期できない**。

次の予約がないユニットこそ、翌日・翌々日に回しても運営上の支障がない。
現状はそこで延期を諦め、Rクリーン（外注）に流れている可能性がある。

### 影響の概算（合成データによる試算）

| 状況 | 外注件数の差 |
|---|---|
| 各ユニットが連続して埋まっている（繁忙期を想定） | **差なし**（最後の予約は14日より先にあり、そもそも外注対象外） |
| ユニットに空き期間がある（閑散期を想定） | **外注が約25%減** |

※ あくまで合成データでの試算。実データでの影響はシャドー運用時に実測する。

### 決定（経営者に確認済み）

**意図した仕様ではなく単なる実装漏れだったため、修正する。**
新実装では次の予約がない場合も +2日 まで延期できる（`allowDeferWithoutNextBooking` の既定値 = true）。

- 害虫防止の「チェックアウト+2日」上限は変わらないため、運用上のリスクはない。
- **これが旧版から意図的に変えた唯一の割り当て挙動**。それ以外は完全に一致している。
- `allowDeferWithoutNextBooking: false` で旧版の挙動を再現できる。
  これは新旧一致テスト（parity）専用のスイッチであり、本番では使わない。

### この修正を守るテスト

| テスト | 内容 |
|---|---|
| 新旧一致（旧版互換モード） | この1点を旧版に戻せば、ランダム2000シナリオで完全一致する＝他に差はない |
| 互換モードを外すと差が出る | 修正が実際に効いていることの確認（比較の形骸化防止） |
| 外注が増えない | 修正版の外注件数が旧版を上回らないことをランダム100シナリオで検証 |
| 害虫防止の絶対条件 | 清掃日が「チェックアウト日 〜 +2日」の範囲を必ず守ることをランダム200シナリオで検証 |

## 2026-09-09 管理画面（Beds24接続・対応づけ・手動実行）

### 背景

M4（ログインとスタッフ画面）まで動いたが、**予約が1件も入らない**状態だった。
原因は `unit_map`（Beds24 の `roomId:unitId` → ユニット名 の対応表）が空だったこと。
この表の値は事業所ごとに違うため初期データに入れられず、旧版でもスプレッドシートの
「設定」シート21行目以降に手で入れていた。つまり**画面がない限り登録手段が無い**。

`fetchBookings` は対応表が空だと例外を投げ、`runDaily` は `zero_bookings` で止まる。
画面上は「予定なし」に見えるだけで原因が分からないため、ここを最優先で作った。

### 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| M5 の順番 | Beds24 接続と対応づけを先に出す | 9ユニットの対応づけが合っているかが最大の未知数。実データを早く入れて確かめる |
| 割り当て一覧 | M5-a では**読み取りのみ** | 手動実行の結果を目で確認できないと検証にならない。手動変更は次 |
| 対応づけの保存 | 丸ごと入れ替え（`replaceUnitMap`）を維持 | 差分更新より単純で、画面に出ているものが全体、という対応が取れる |
| 対応づけ画面の行 | 「発見した組み合わせ」と「登録済みの対応」の**和集合**を出す | 丸ごと入れ替えのため、取得期間にたまたま予約が無かった部屋を画面に出さないと、保存した瞬間にその対応が消える |
| 招待コード | 画面・実行ログ・通知のどこにも残さない | パスワードと同じ機密。失敗時もフォームは空にして再入力させる |

### `/setup` にログインを要求するようにした

**管理者が1人でも居る場合は、管理者ログインを必須にした。**
まだ誰も居ないときだけ無認証で通す（そうしないと最初の1人を作れない）。

- それまでは、URLを知っている人なら誰でも DB の状態（テーブル・件数）を見られた
- デプロイ直後〜最初に `/setup` を開くまでの間は、先に開いた人が管理者パスワードを
  受け取れてしまう。この窓は**最初の `/setup` を開いた時点で閉じる**ので、
  デプロイしたらすぐ開いてもらう手順にしている

管理者パスワードを控え損ねた場合の復旧は、**D1 の Console で1行消して `/setup` を開き直す**
（`DELETE FROM users WHERE login_id = 'admin';`）。
専用のリセットURLは**作らない**。誰でも叩けてしまい、乗っ取りの入口になるため。

### `/setup/keys` は登録済みなら鍵を作り直さない

`/setup` と `/setup/keys` はアドレス欄の補完で取り違えやすく、実際に間違えて開かれた。
そこで `/setup/keys` の冒頭に `/setup` への案内を置き、
**両方の Secret が登録済みなら新しい鍵を生成しない**ようにした。

作り直して登録し直すと実害が出るため、生成しないこと自体が安全策になる。

- `SESSION_PEPPER` を変える → 全員がログインできなくなる（保存済みハッシュと照合できない）
- `TOKEN_ENC_KEY` を変える → Beds24 のトークンを復号できず、招待コードからの再接続が必要

### 手動実行と無料プランの制限

`/admin/run` は日次処理をその場で回す。無料プランの制限との関係は次のとおり。

| 制限 | 実際 | 判断 |
|---|---|---|
| CPU 10ms / リクエスト | fetch の待ち時間とページ間の 500ms は CPU 時間に入らない | 問題なし |
| サブリクエスト 50 / リクエスト | 認証1回 + 予約取得 最大20ページ = 21回 | 上限内。`MAX_PAGES` が蓋になっている |

実時間では10秒以上かかりうるため、画面に「20秒ほどかかることがあります」と明記した。

## 2026-09-09 Slack 通知と死活監視（M6）

### 背景

旧 GAS 版は本番から外れた（Beds24 のトークンが失効したまま停止）。経営者の判断で
**旧版には戻さない**。したがって並行稼働による突き合わせ検証はできず、
新システムが唯一の本番になった。

この状態で一番危ないのは、旧版で実際に起きたのと同じこと——
**静かに止まって誰も気づかない**まま清掃予定が更新されなくなることである。
記録の仕組み（runs / notifications）は入っていたが、見に行かないと分からなかった。

### 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| 記録と送信 | **分ける**。ジョブは記録するだけ、送信は別ジョブ | Slack が落ちても割り当ては止めない。復旧後に自動で送り直せる |
| 送信の失敗 | ジョブの成否に影響させない（`finally` で送り、例外は握る） | 通知が原因で清掃の割り当てが止まるのは本末転倒 |
| 再送 | `sent_at` が空のものを次回に再送。ただし72時間以内のものだけ | 後から Slack を設定したときに、何日も前の警告がまとめて流れないように |
| 正常時の通知 | **既定でオン**（1日1回） | 「いつも届くものが届かない」ことが、止まっていることに気づく手がかりになる。設定で切れる |
| Webhook URL | Beds24 トークンと同じ鍵で暗号化して保存し、画面に再表示しない | URL を知っていれば誰でもそのチャンネルに投稿できるため |
| 鍵が変わった場合 | 例外にせず「未設定」として扱う | ここで投げるとジョブごと止まる |

### `/api/health` は異常時に 503 を返す

Slack 通知には弱点がある。**システムごと止まったときは、通知を送る側も止まっている。**
これを補うには外から叩いてもらうしかない。

無料の監視サービスはステータスコードしか見ないものが多いため、
**判定をサーバー側に持たせて 503 を返す**設計にした。利用者は URL を登録するだけで済む。

異常と見なす条件:

- 初期データが入っていない
- Beds24 が「要再接続」
- 自動実行が `stale_run_alert_days`（既定3日）以上 成功していない
- SESSION_PEPPER が変わっていて誰もログインできない

**まだ一度も実行していない状態は異常にしない**（セットアップ中に 503 が出ると混乱するため）。

### 残っている検証の穴

旧版との突き合わせができなくなったため、「Beds24 の生データを正しく解釈できているか」は
実データを見て確認するしかない。割り当てエンジン自体は旧版とランダム2000シナリオで一致しているので、
残るリスクは**ユニット対応づけ（unit_map）の誤り**に絞られる。
旧スプレッドシートの「割り当て結果」シートは残っているので、数件だけでも突き合わせること。

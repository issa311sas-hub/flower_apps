# 設計判断ログ（cleaning-schedule）

`apps/schedule-auto-assign/docs/decisions.md`（GAS 版 v1〜v8）の続き。
業務ルールそのものの経緯は旧アプリのログを参照すること。ここには Web 版の判断を記録する。

---

## 2026-09-08 Web アプリ化の方針決定

### 背景

清掃スタッフが Google カレンダーを使いこなせず、スマホの容量を理由にアプリも入れられない。
現行仕様は「カレンダーに数字の入力がない日＝出勤不可」というフェイルセーフのため、
**入力が定着しないことがそのまま Rクリーン外注のコスト増につながる**構造になっていた。

### 決定事項（経営者と確認済み）

| 項目 | 決定 |
|---|---|
| 移行方法 | 一気に完全移行。GAS + スプレッドシートは廃止（旧アプリは凍結して残す） |
| Google カレンダー | 完全にやめる。Web アプリを唯一の正とする |
| ログイン | 管理者が ID とパスワードを発行して各自に配る（厳密なセキュリティは不要） |
| 管理画面 | Web の管理画面も作る |
| 異常通知 | Slack の Incoming Webhook（＋管理画面のバナー） |
| 公開URL | `*.workers.dev` のまま（独自ドメインなし） |
| 完了報告ボタン | 入れる（現行にない新機能） |
| 既存の割り当て | 移行せず、新システムで全部再計算する |

### 技術方針

- **採用: Cloudflare Workers（静的アセット）+ D1 + Cron Triggers**
  - 当初の要望は Cloudflare Pages だったが、**Pages Functions は Cron Triggers に対応していない**。
    日次の自動実行がこのシステムの中心であるため、Pages 単体では成立しない。
    現在の Workers は静的配信で Pages と同等のため、デプロイ単位を1つにまとめられる Workers を選んだ。
- **不採用: SPA（React/Preact 等）** → 利用者は非エンジニアで端末も古い。画面は一覧とフォームのみで、
  フレームワークが買うものがない。サーバーレンダリングなら初回表示が速く、JS が壊れても画面は出る。
- **不採用: KV / Durable Objects** → D1 だけで足りる（セッション・設定・スロットルもテーブルで持つ）。
- **Beds24 のリフレッシュトークンは D1 に暗号化して保存する**
  → Cloudflare の Secrets は実行中に書き換えられないが、Beds24 はトークン取得のたびに
    ローテーションするため、Secrets には置けない（暗号鍵だけを Secret にする）。

### 日付の扱い（移行で最も壊れやすい点）

GAS はスクリプトのタイムゾーン（JST）で動いていたが、**Workers は UTC**。
そのため以下を規約とし、`test/core/purity.test.js` で機械的に検査する。

- カレンダー上の1日は必ず `'YYYY-MM-DD'` の文字列で表す
- 日付演算は `src/core/dates.js` に閉じる。`new Date(y, m, d)` と `setDate()` は使わない
- 実時刻に触れてよいのは `jstToday()` / `nowIso()` のみ
- cron は UTC 指定（`0 21 * * *` = 翌日 06:00 JST）

## 2026-09-08 割り当てエンジンの移植方針

8版かけて実運用で調整されたロジックのため、**まず現行と同一挙動で移植し、
テストで固定してから改善を検討する**という順序を徹底する。

### 新旧一致テスト（parity test）

旧 GAS 版の `doMatching_` をほぼバイト単位でコピーした比較用エンジン
（`test/legacy/legacy-engine.mjs`。I/O の4か所と実行日だけを引数に差し替えたもの）を用意し、
シード固定のランダムシナリオ2000件（延べ10万件以上の割り当て）で
新実装との出力一致を検証している。**現時点で完全一致。**

### 意図的に変えた点

1. **スタッフ名のベタ書きを廃止**し、`priority` 順のループに一般化した。
   旧版は「細田さん・普久原さん・福田さん」を名前で直接参照し、3名揃わないと例外を投げていた
   （FAQ「スタッフを追加・変更したい → コード変更が必要」の原因）。
   3名・同じ順序であれば計算結果は旧版と完全に一致する。
2. **Rクリーンを `kind: 'outsource'`** として扱う（旧版は文字列 'Rクリーン' を直接比較）。
3. **`isManual`（管理者の手動変更）の行を全フェーズで凍結する**。
   旧版に対応する処理はなく、Google カレンダー側の「同期状態=手動」が担っていた役割を移した。
   凍結された行も枠（usage）は消費する。
4. 日付を Date から文字列に変更（上記のとおり）。

### 現状維持とした「癖」（移植では直さない）

| 箇所 | 現行の挙動 | 扱い |
|---|---|---|
| Phase 2.5（Code.gs:835） | 入れ替え判定で既定上限を 0 固定にし、設定値を無視 | 既定値が全員0の現在は無害。そのまま移植 |
| Phase 3・4 | `usageByDate` を更新しない | そのまま移植 |
| Phase 4（Code.gs:915） | コスト最適化を「その予約のゲスト数」で比較。外注費は本来「次に泊まる人数」に連動するのでは | ⚠ 稼働後に経営者へ確認 |
| `computeDiff_` | 変更検知はチェックアウト日とユニットのみ（タイトル変更では再割り当てしない） | v7 の意図的な修正。維持 |

## 2026-09-08 【修正済み】次の予約がないユニットが延期できなかった件

### 見つかったこと

`docs/requirements.md` と旧 `decisions.md` には清掃期限を

> 清掃期限 = min(次の予約の開始日 - 1日, チェックアウト日 + 2日)

と記載しているが、**実装はそうなっていない**（`Code.gs:488, 500-509`）。
次の予約が見つからない場合、期限はチェックアウト**当日**のままで、
`canDefer` が false になる。つまり **次の予約がないユニットは1日も延期できない**。

次の予約がないユニットこそ、翌日・翌々日に回しても運営上の支障がない。
現状はそこで延期を諦め、Rクリーン（外注）に流れている可能性がある。

### 影響の概算（合成データによる試算）

| 状況 | 外注件数の差 |
|---|---|
| 各ユニットが連続して埋まっている（繁忙期を想定） | **差なし**（最後の予約は14日より先にあり、そもそも外注対象外） |
| ユニットに空き期間がある（閑散期を想定） | **外注が約25%減** |

※ あくまで合成データでの試算。実データでの影響はシャドー運用時に実測する。

### 決定（経営者に確認済み）

**意図した仕様ではなく単なる実装漏れだったため、修正する。**
新実装では次の予約がない場合も +2日 まで延期できる（`allowDeferWithoutNextBooking` の既定値 = true）。

- 害虫防止の「チェックアウト+2日」上限は変わらないため、運用上のリスクはない。
- 旧版から意図的に変えた割り当て挙動のひとつ（もうひとつは 2026-09-09 の「外注の引き戻し」）。
  それ以外は完全に一致している。
- `allowDeferWithoutNextBooking: false` で旧版の挙動を再現できる。
  これは新旧一致テスト（parity）専用のスイッチであり、本番では使わない。

### この修正を守るテスト

| テスト | 内容 |
|---|---|
| 新旧一致（旧版互換モード） | この1点を旧版に戻せば、ランダム2000シナリオで完全一致する＝他に差はない |
| 互換モードを外すと差が出る | 修正が実際に効いていることの確認（比較の形骸化防止） |
| 外注が増えない | 修正版の外注件数が旧版を上回らないことをランダム100シナリオで検証 |
| 害虫防止の絶対条件 | 清掃日が「チェックアウト日 〜 +2日」の範囲を必ず守ることをランダム200シナリオで検証 |

## 2026-09-09 管理画面（Beds24接続・対応づけ・手動実行）

### 背景

M4（ログインとスタッフ画面）まで動いたが、**予約が1件も入らない**状態だった。
原因は `unit_map`（Beds24 の `roomId:unitId` → ユニット名 の対応表）が空だったこと。
この表の値は事業所ごとに違うため初期データに入れられず、旧版でもスプレッドシートの
「設定」シート21行目以降に手で入れていた。つまり**画面がない限り登録手段が無い**。

`fetchBookings` は対応表が空だと例外を投げ、`runDaily` は `zero_bookings` で止まる。
画面上は「予定なし」に見えるだけで原因が分からないため、ここを最優先で作った。

### 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| M5 の順番 | Beds24 接続と対応づけを先に出す | 9ユニットの対応づけが合っているかが最大の未知数。実データを早く入れて確かめる |
| 割り当て一覧 | M5-a では**読み取りのみ** | 手動実行の結果を目で確認できないと検証にならない。手動変更は次 |
| 対応づけの保存 | 丸ごと入れ替え（`replaceUnitMap`）を維持 | 差分更新より単純で、画面に出ているものが全体、という対応が取れる |
| 対応づけ画面の行 | 「発見した組み合わせ」と「登録済みの対応」の**和集合**を出す | 丸ごと入れ替えのため、取得期間にたまたま予約が無かった部屋を画面に出さないと、保存した瞬間にその対応が消える |
| 招待コード | 画面・実行ログ・通知のどこにも残さない | パスワードと同じ機密。失敗時もフォームは空にして再入力させる |

### `/setup` にログインを要求するようにした

**管理者が1人でも居る場合は、管理者ログインを必須にした。**
まだ誰も居ないときだけ無認証で通す（そうしないと最初の1人を作れない）。

- それまでは、URLを知っている人なら誰でも DB の状態（テーブル・件数）を見られた
- デプロイ直後〜最初に `/setup` を開くまでの間は、先に開いた人が管理者パスワードを
  受け取れてしまう。この窓は**最初の `/setup` を開いた時点で閉じる**ので、
  デプロイしたらすぐ開いてもらう手順にしている

管理者パスワードを控え損ねた場合の復旧は、**D1 の Console で1行消して `/setup` を開き直す**
（`DELETE FROM users WHERE login_id = 'admin';`）。
専用のリセットURLは**作らない**。誰でも叩けてしまい、乗っ取りの入口になるため。

### `/setup/keys` は登録済みなら鍵を作り直さない

`/setup` と `/setup/keys` はアドレス欄の補完で取り違えやすく、実際に間違えて開かれた。
そこで `/setup/keys` の冒頭に `/setup` への案内を置き、
**両方の Secret が登録済みなら新しい鍵を生成しない**ようにした。

作り直して登録し直すと実害が出るため、生成しないこと自体が安全策になる。

- `SESSION_PEPPER` を変える → 全員がログインできなくなる（保存済みハッシュと照合できない）
- `TOKEN_ENC_KEY` を変える → Beds24 のトークンを復号できず、招待コードからの再接続が必要

### 手動実行と無料プランの制限

`/admin/run` は日次処理をその場で回す。無料プランの制限との関係は次のとおり。

| 制限 | 実際 | 判断 |
|---|---|---|
| CPU 10ms / リクエスト | fetch の待ち時間とページ間の 500ms は CPU 時間に入らない | 問題なし |
| サブリクエスト 50 / リクエスト | 認証1回 + 予約取得 最大20ページ = 21回 | 上限内。`MAX_PAGES` が蓋になっている |

実時間では10秒以上かかりうるため、画面に「20秒ほどかかることがあります」と明記した。

## 2026-09-09 Slack 通知と死活監視（M6）

### 背景

旧 GAS 版は本番から外れた（Beds24 のトークンが失効したまま停止）。経営者の判断で
**旧版には戻さない**。したがって並行稼働による突き合わせ検証はできず、
新システムが唯一の本番になった。

この状態で一番危ないのは、旧版で実際に起きたのと同じこと——
**静かに止まって誰も気づかない**まま清掃予定が更新されなくなることである。
記録の仕組み（runs / notifications）は入っていたが、見に行かないと分からなかった。

### 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| 記録と送信 | **分ける**。ジョブは記録するだけ、送信は別ジョブ | Slack が落ちても割り当ては止めない。復旧後に自動で送り直せる |
| 送信の失敗 | ジョブの成否に影響させない（`finally` で送り、例外は握る） | 通知が原因で清掃の割り当てが止まるのは本末転倒 |
| 再送 | `sent_at` が空のものを次回に再送。ただし72時間以内のものだけ | 後から Slack を設定したときに、何日も前の警告がまとめて流れないように |
| 正常時の通知 | **既定でオン**（1日1回） | 「いつも届くものが届かない」ことが、止まっていることに気づく手がかりになる。設定で切れる |
| Webhook URL | Beds24 トークンと同じ鍵で暗号化して保存し、画面に再表示しない | URL を知っていれば誰でもそのチャンネルに投稿できるため |
| 鍵が変わった場合 | 例外にせず「未設定」として扱う | ここで投げるとジョブごと止まる |

### `/api/health` は異常時に 503 を返す

Slack 通知には弱点がある。**システムごと止まったときは、通知を送る側も止まっている。**
これを補うには外から叩いてもらうしかない。

無料の監視サービスはステータスコードしか見ないものが多いため、
**判定をサーバー側に持たせて 503 を返す**設計にした。利用者は URL を登録するだけで済む。

異常と見なす条件:

- 初期データが入っていない
- Beds24 が「要再接続」
- 自動実行が `stale_run_alert_days`（既定3日）以上 成功していない
- SESSION_PEPPER が変わっていて誰もログインできない

**まだ一度も実行していない状態は異常にしない**（セットアップ中に 503 が出ると混乱するため）。

### 残っている検証の穴

旧版との突き合わせができなくなったため、「Beds24 の生データを正しく解釈できているか」は
実データを見て確認するしかない。割り当てエンジン自体は旧版とランダム2000シナリオで一致しているので、
残るリスクは**ユニット対応づけ（unit_map）の誤り**に絞られる。
旧スプレッドシートの「割り当て結果」シートは残っているので、数件だけでも突き合わせること。

## 2026-09-09 担当の手動変更とタイムライン（M5-b）

### 「固定を解除する」と「担当を決め直す」を分けた

実装中に、割り当てエンジンの挙動を取り違えていたことが分かった。

`is_manual` を外しても、**次の自動実行で担当は決め直されない**。
エンジンは予約に変更がなければ前回の担当をそのまま引き継ぐ（`src/core/assign.js` の Phase 0）。
無用な入れ替えを避けるための設計で、これは旧版から引き継いだ正しい挙動である。
`is_manual` が効くのは、予約が変わったときと、後半の再調整フェーズ（2.5/3/4）だけ。

つまり「自動に戻す」というボタン1つでは、利用者の期待（決め直してほしい）と
実際の動き（担当は変わらない）がずれる。そこで操作を2つに分けた。

| ボタン | 動き | 使う場面 |
|---|---|---|
| **固定を解除する** | `clearManual` のみ。担当はそのまま、以後の再調整の対象に戻る | 手動で決めた担当を、そのまま生かしたい |
| **担当を決め直す** | 未割当に戻し、清掃日も退去日に戻してから固定を解除 | あとから出勤入力が増えたので選び直したい |

画面の文言も「担当がすぐ変わるわけではありません」と明記した。
テストでも両方の挙動を固定している（実際に `runDaily` を回して確認）。

### 状態（status）は選ばせない

手動変更の画面では担当と清掃日だけを選ばせ、状態は担当から導出する。
`statusFor` を `src/core/assign.js` から export して再利用した。
判定を画面側にもう一度書くと、自動と手動で状態がずれる。

### 清掃日の範囲はサーバー側で必ず検査する

「チェックアウト日 〜 +max_defer_days」は害虫防止の絶対条件で、
parity テストで守っていることを検証している唯一の不変条件。
手動変更でも破らせない。範囲外は理由（何日まで指定できるか）を添えて拒否する。

旧版は Google カレンダーを直接編集できたため、この制約は破れる状態だった。
Web アプリ化で意図的に締めた点になる。

### タイムラインの下段に出勤枠を並べた

ユニット×日付の表だけでは「なぜ外注になったのか」が分からない。
同じ画面の下に各スタッフの出勤枠を並べ、**未入力は `-`（赤）**で区別した。
外注や未割当が出ている日は、たいてい真下の枠が 0 か未入力になっている。
入力漏れがそのまま外注コストになる、という因果を1画面で見せるのが目的。

## 2026-09-09 【修正済み】外注に落ちた清掃を取り戻せなかった件

### 症状

運用開始直後、「細田さんを 9/10 に3件可能にしても、Rクリーン（外注）のまま
割り当てられない」と報告があった。エンジンで再現し、原因を確定させた。

```
既存なし（初回）      → 細田さん / 確定
既に外注（出勤入力後）→ Rクリーン / 外注   ← これ
既に未割当            → 細田さん / 確定
```

### 原因

1. 初回実行の時点で出勤入力が1件も無く、今後14日分がすべて未割当 →
   Phase 3 の安全ネットで外注に落ちた
2. その後に出勤可能件数を入れても、予約自体は変わっていないので
   Phase 0 が前回の担当（外注）をそのまま引き継ぐ
3. Phase 1.5 / 2 / 2.5 / 3 はいずれも**担当が「未割当」の行しか対象にしない**。
   一度 外注 になった行を取り戻す処理がどこにも無かった

唯一の例外が Phase 0 の「14日以上先の外注は未割当に戻す」。実測した境界:

| 清掃日 | 結果 |
|---|---|
| 1日後・13日後 | 外注のまま |
| 14日後・21日後 | スタッフに戻る |

**これは移植ミスではなく旧 GAS 版と同じ挙動。** 旧版は出勤予定が常に先に
入っていたため表面化しにくかったが、今回は出勤入力が空の状態で初回実行したため、
直近14日分がまるごと外注に固定された。外注は実費なので放置できない。

### 決定: Phase 1.4「外注の引き戻し」を追加する（旧版から意図的に変えた2点目）

Phase 1 のあと・Phase 1.5 の前に、**非手動・未完了・今日以降**の外注行を見て、
その清掃日に空き枠のあるスタッフがいれば未割当に戻す。あとは Phase 1.5 が拾う。

`params.reclaimOutsourced`（既定 true）で切り替えられる。
parity テストの `LEGACY_COMPAT` に `reclaimOutsourced: false` を足したので、
ランダム2000シナリオの完全一致は従来どおり通る。

触らないもの:

| 対象 | 理由 |
|---|---|
| `isManual` | 管理者が手で決めたものを勝手に動かさない |
| `completedAt` あり | 終わった清掃を別の人の担当にしない |
| `cleaningDate < today` | 過去は書き換えない |

> 副作用として、外注に出すつもりだった仕事が前日に引き戻されることがありうる。
> 「スタッフが空いているのに外注費を払う」より明らかにましなので既定は有効にする。
> 実運用で連絡の行き違いが起きるようなら「◯日前を切ったら引き戻さない」設定を足す。

### あわせて: 「ゼロから割り当て直す」

引き戻しは「空き枠のあるスタッフがいる日」だけが対象なので、確実に作り直せる手段も用意した。
`resetAllAssignments`（`src/db/assignments.js`）で未割当に戻してから実行する。

**行は消さない。** 消すと完了報告と手動固定が失われる。未割当に戻して清掃日も退去日に戻し、
そのあとの自動実行に決め直させる。1件版の `resetAssignment` と同じ考え方。

### この件から得た教訓

**空のデータで初回実行すると、その結果が居座る。**
割り当てエンジンは「前回の担当を引き継ぐ」設計（無用な入れ替えを避けるため）なので、
初期状態が悪いとそれが固定される。移行時は「出勤入力を入れてから初回実行する」か、
作り直しボタンを使うこと。手順書にもその順序で書いてある。

## 2026-09-09 出勤入力にカレンダー画面を足し、既定にした

### 背景

出勤入力は1日1行の縦長リスト（一覧入力）だけだった。31行を上から埋める形で、
月全体の形が見えず「どの週が空いているか」が分からない。

この移行はそもそも**スタッフが Google カレンダーを使いこなせなかった**ことが理由なので、
入力画面の分かりやすさが移行の成否そのもの。カレンダーの見た目を既定にした。

### 保存の仕組みは1つに保つ

カレンダーのマスも一覧の行も、中身は**同じ `cap_YYYY-MM-DD` のラジオボタン**。
月まとめて1回 POST するのも同じ。画面が2つあっても保存処理は1つで済む。

JavaScript がやるのは「どのラジオを選ぶか」だけで、値の持ち方や送信には関与しない。
テストでも「同じ内容を送れば両方の画面で同じ結果になる」ことを固定した。

### 2タップ方式にした（モードを持たせない）

マスを押す → 下のピッカーで件数を選ぶ、の2タップ。
「いま3件モード」のような状態を持たせれば1タップで塗れるが、
**押し間違いに気づけなくなる**ため採らなかった。
1日ずつだと31タップになる問題は、従来どおり「まとめて入力」で解く。

ピッカーはマスごとに置かず、共通のものを1つだけ使う（マスごとだと画面が埋まる）。

### 「未入力に戻す」を足した

これまで一度入れた値を未入力に戻す手段がなかった。カレンダーは押し間違いが起きやすく、
管理画面（`/admin/availability`）では「-（未入力）」と「0件」を別物として見せているので、
戻せないと実態とずれる。`value="-1"` を「消す」として扱い、`clearCapacity` を呼ぶ。

### JavaScript 前提を画面単位に緩めた

これまでは「JSが動かなくても全機能が使える」という方針だったが、
カレンダーのピッカーは JS が要る。方針は**画面単位で受け皿を用意する**形に改めた。

- カレンダー … JS 必須。動かない場合は `<noscript>` で一覧入力に案内する
- 一覧入力 … JS なしで完全に動く（従来どおり）

入力手段が失われないことは保証したうえで、既定の画面は分かりやすさを優先した。

## 2026-09-09 清掃完了報告と現地精算の集計

### 背景

「清掃おわりました」ボタンは完了時刻を記録するだけで、実際の完了報告
（使用状況・設備の確認・追加サービス・現地精算金額）はメッセージで送ってもらっていた。

**現地精算金額**は、お客さんが追加サービスの料金を現地に置いていき、清掃員が回収した額。
事実上の**給与の前払い**なので、あとで給与から差し引く必要がある。
旧運用では月末にメッセージを遡って手で足していた。ここを自動化するのが今回の主目的。

### 先に直したこと: マイグレーションが本番に流れなかった

`applyMigrations` は「初期データが入っていたら何もしない」設計で、
**本番DBはすでに seed 済みなので、新しいテーブルを足す手段がなかった**。

`schema_migrations` に適用済みを記録し、未適用のものだけ流す形に変えた。
記録が1つも無いDB（この仕組みを入れる前のもの）は、現物を見て
0001/0002 を「適用済み」として引き継ぐ。流し直すと「テーブルが既にある」で落ちるため。

あわせて、対象ファイルを書き並べていた箇所を2つ直した。どちらも黙って古くなる書き方だった。

- `src/db/migrations.js` に一覧を集約し、`src/index.js` とテストの両方から使う。
  `migrations/` の中身と一致しているかをテストで検査する
- `tools/build-console-sql.mjs` が `migrations/*.sql` を全部読むようにした

未適用があると `/api/health` が 503 を返す。スキーマが古いままだとアプリが正しく動かないので、
デプロイ後に `/setup` を開き忘れたことを外部監視で気づけるようにした。

### 金額の記録を予約に紐づけない

`assignments` は `bookings(booking_id) ON DELETE CASCADE` で、`saveAssignments` は
取得結果から消えた予約の行を削除する。**報告を素直に booking_id で紐づけると、
キャンセル1件で回収済み現金の記録が消える。**

そこで `completion_reports` は `booking_id` に外部キーを張らず、
清掃日・ユニット・担当者名・金額を自前で持つ。テストでも
「予約がキャンセルされて割り当てが消えても、集計に残る」ことを固定した。

### 項目は設定で変えられるが、過去の報告は当時のまま

設備・追加サービスの項目は全ユニット共通で、`settings` に1行1項目で持つ
（`report_equipment` / `report_services`）。管理画面のテキストエリアで編集できる。

回答は `report_answers` に**その時の項目名ごと**保存する。
あとから項目を変えても過去の報告が壊れない。

### 追加サービスは3択

「ありorなし、清掃したかどうか」という元の様式をそのまま
`なし / あり（清掃済）/ あり（未清掃）` の3択にした。
2択にすると「使ったが清掃していない」状態を追えなくなる。

### すぐ知るべきことだけ Slack に流す

使用状況 **F**（受け入れ拒否）、設備に **✕**、**現地精算 > 0** のいずれかで通知する。
どれも「あとで気づけばいい」ものではないので `throttleHours: 0` で1件ずつ積み、
報告の保存直後に送信する。**送信に失敗しても報告は成立させる**（管理画面には残る）。

## 2026-09-09 データベースの更新を管理画面から当てられるようにした

### 何が起きたか

`0003` を追加してデプロイしたあと、本番で未適用のまま残った。
`/api/health` は正しく検知していた（`pendingMigrations` に3件、`ok: false`、503）。

**原因は仕組みではなく導線。** `/setup` は管理者が居る場合ログインを要求するため、
ログインしていない状態で開くとログイン画面に飛ばされ、適用処理まで到達しない。
利用者から見ると「案内されたURLを開いたのに何も起きない」。

`schema_migrations` だけ存在して空だったのは、`/api/health` が
`listPendingMigrations` を呼んだ際にテーブルだけ作られたため。

### 直したこと

| | |
|---|---|
| **管理画面から1クリック** | 管理者はその時点でログイン済み。`/admin` の最上部に未適用の件数と「いま更新する」を出す |
| **自動実行でも当てる** | `scheduled()` でジョブの前に適用する。誰も画面を開かなくても翌朝には当たっている |
| **文言** | `/api/health` の案内を「/setup を開いて」から「管理画面で更新する」に変えた |

自動適用は各マイグレーションごとに `db.batch`（＝1トランザクション）なので、
途中まで適用されて壊れることはない。失敗したら通知に積み、ジョブ本体は続行する。

### マイグレーションは流し直しても壊れないようにする

テストで「記録だけ消えて表は残っている」状態を作ったところ、
`0003` の `INSERT INTO settings` が主キー重複で落ちた。
**途中まで適用された状態から流し直す**ことは起こりうるので、
初期データの投入は `INSERT OR IGNORE` にした。

なお `0003` はすでに本番に適用済みなので、この変更が流れ直すことはない
（今後の新規セットアップとテストにだけ効く）。

### 教訓

`/api/health` が異常を正しく検知していても、**直し方の導線が塞がっていれば直らない**。
「気づける」だけでなく「その場で直せる」ところまでを一組にする。

**2. `unassigned` は消さない。**
あれは「いまの状態」を伝えるもので、実行が成功しても未割当は残りうる。
消すとスロットル（12時間）のせいで次の実行でも積み直されず、

```sql
SELECT MAX(finished_at) FROM runs WHERE ok = 1 AND kind IN ('cron', 'manual')
```

- `last_success_run_at` は表示用に残すが、判定には使わない

- `/api/health` … `neverRun` も 503 にする
- `/admin` … 「まだ一度も」と「途中で止まった」を分けて出し、
  前者では Cron Triggers の確認先まで案内する（原因が違うので対処も違う）

**監視の仕組みは、それ自体が壊れていないことを確かめないと意味がない。**

## 2026-09-10 cron が呼ばれたこと自体を記録する

### きっかけ

利用者から「朝6時に自動で実行されていないようだ」と指摘を受けた。
9/9 21:00 UTC（= 9/10 06:00 JST）の実行ログが無い。調べた結果は次のとおり。

| 調べたこと | 結果 |
|---|---|
| Cloudflare の Cron Triggers | 2件とも正しく登録されている（21:00 / 09:00 UTC） |
| `wrangler.jsonc` の `triggers` | 9/8 18:29 UTC から入っている。最初のデプロイから有効 |
| `scheduled()` の実装 | 正しい |
| デプロイとの衝突 | **無い**。直前の push は 19:10 UTC（約2時間前）、次は翌 06:43 UTC |

当初「デプロイと重なった取りこぼし」と推測したが、**時刻を確認したら成り立たなかった**。
推測を先に置いて、それに合う説明を探していた。順序が逆だった。

### 本当の問題

原因が分からないことではなく、**分けられない**ことだった。

実行の行（`runs`）は処理が始まってから作られる。その手前で落ちた場合も、
Cloudflare から呼ばれなかった場合も、**どちらも「記録が無い」という同じ見え方**になる。
対処はまったく違う（前者はアプリの問題、後者は Cloudflare の設定の問題）のに、
記録からは区別できない。

Cloudflare の Observability を見れば分かるが、それは毎回ダッシュボードを掘るということ。
**アプリが自分で言えるようにする。**

### 直したこと

**1. `scheduled()` のいちばん最初に、呼ばれた事実を記録する。**

```js
// ★何よりも先に「呼ばれた」ことを記録する。
await recordCronEvent(env.DB, event.cron);
```

`settings` に `last_cron_event_at` と `last_cron_expression` を書く。
書き込みは try/catch で握り、**記録に失敗しても本処理は必ず続ける**
（記録のために業務を止めない）。マイグレーションの自動適用より前に置く。

以後、どこで落ちても「呼ばれた事実」だけは残る。

**2. 「呼ばれていない」を独立した警告にする。**

`getCronHealth`（`src/db/runs.js`）を `getRunHealth` と並べて置いた。
2日間呼ばれていなければ異常とする（cron は1日2回動くので、2日空けば確実におかしい）。

- `/api/health` … `lastCronEventAt` / `lastCronExpression` を返し、`problems` に加える → 503 → UptimeRobot
- `/admin` … 原因ごとに3種類の案内を出し分ける

| 状態 | 意味 | 案内先 |
|---|---|---|
| 呼ばれていない | Cloudflare の設定の問題 | Cron Triggers |
| 呼ばれたが一度も成功していない | アプリの問題 | 実行ログ |
| 動いていたのに止まった | アプリの問題 | 実行ログ |

### テストで押さえたこと

`test/web/cron-health.test.js`。いちばん大事なのは最後の1つ。

- 処理が失敗しても `last_cron_event_at` は残る
- どちらの cron かが記録される（日次と見張りで値が変わる）
- 記録に失敗しても本処理は動く
- 2日以上呼ばれていなければ `/api/health` が 503 になる
- **呼ばれているのに失敗しているときは「呼ばれていない」とは言わない**

最後の1つが無いと、アプリの不具合を Cloudflare のせいだと案内してしまう。
今回の改修の目的そのものが裏返る。

### 教訓

**「記録が無い」は情報ではない。**

## 2026-09-10 【修正済み】死活監視の HEAD が404だった件

### 見つかった経緯

cron の件を追って Cloudflare の Observability を眺めていて、並びに気づいた。

```
15:52:27  HEAD /api/health
15:52:45  GET  /api/health     ← 18秒後
15:47:06  HEAD /api/health
15:47:22  GET  /api/health     ← 16秒後
```

**UptimeRobot はまず HEAD で叩き、失敗したら GET でやり直す。**
`src/router.js` の `match()` はメソッド完全一致で、`/api/health` は GET しか
登録していなかった。つまり HEAD は毎回404を返していた。

### なぜ気づけなかったか

**GET のやり直しが通るので、監視は成立していた。** 表からは何も見えない。

しかし実害はあった。

- 1回の巡回が2往復になり、検知が最大18秒遅れる
- 監視を「HEAD のみ」に設定すると、**健全なのに常時停止と誤検知する**

死活監視の窓口が、監視のやり方しだいで嘘をつく状態だった。
これは今日直した3件（警告が消えない／滞留の時計がリセットされる／
呼ばれたか分からない）と**まったく同じ形**をしている。
監視の仕組みそのものが検証されていなかった。

### 直したこと

`match()` に、HEAD で一致が無ければ GET を探すフォールバックを足した。
HTTP の規定どおり（HEAD は GET と同じ状態・ヘッダを返し、本文だけ返さない）で、
`/api/health` 専用にはしていない。数行で全ルートが正しくなる。

本文は `fetch` の出口でまとめて落とす。Cloudflare の実行環境も落としてくれるが、
明示しないとテストで確かめられない。死活監視が通る経路を実環境まかせにはしない。

### テストで押さえたこと

`test/web/head.test.js`。大事なのは次の2つ。

- **異常時は HEAD でも 503 を返す** … 「HEAD だと常に 200」では監視の意味が無い
- **POST 専用のパス（`/admin/run`）は HEAD でも 404 のまま** …
  HEAD を GET 扱いにする際にメソッドの区別まで崩すと、
  副作用のある処理を GET で叩けてしまう

### 教訓

**監視は「通っていること」ではなく「正しい経路で通っていること」を確かめる。**
今回は結果的に通っていたので、ログの並びを見るまで誰も気づけなかった。
